# 多 Agent 项目分步骤实施计划

编写日期：2026-10-13。

实施目录：`D:\My_workspace\Multi-agent\Multi-agent`。

本计划按当前代码重新核对。现在注册数据库、网络搜索、知识库三个子 Agent，使用 Deep Agents 0.4.3；主执行入口为异步流式调用，但配置的是同步 SqliteSaver。当前没有反思检查模块、共享摘要模块、Skill 目录和会话历史存储模块。不要将之前其他工作区的模块视为已经存在。

本文只安排开发步骤。文件名、测试用例和新接口均为计划内容；本次未创建这些业务模块、未安装依赖、未运行测试、未启动项目。

## 一、执行顺序与首版范围

按以下顺序开发，每一步达到完成条件后再进入下一步：

```text
01 固定当前代码与环境
 → 02 验证框架接口，决定是否升级
 → 03 修复异步执行与资源管理
 → 04 为每轮任务建记录
 → 05 统一事件保存和推送
 → 06 建立 Hook 执行入口
 → 07 接入工具校验与次数限制
 → 08 统一子 Agent 注册与触发入口
 → 09 增加子 Agent 结果检查
 → 10 保存并传递合格查询结果
 → 11 接入 Skill 读取
 → 12 实现指定业务流程的前置条件
 → 13 增加超时、取消和事件补发
 → 14 完成前端与整体功能验收
```

首版保留现有三个子 Agent，使用单服务进程和 SQLite。先实现两个 Skill、固定顺序的 Hook、可追踪的子任务执行，不增加动态生成 Agent、任意脚本执行、分布式调度和写库操作。

### 每步通用交付要求

- 修改前确认当前 Git 状态，保留用户已有修改。
- 每步单独提交，提交说明写清新增行为与验证结果；不要把环境升级和所有功能合成一个大提交。
- 检查命令和实际输出保存在该步记录中；尚未执行的检查明确标为“未执行”。
- 验收失败就修复该步，不在失败链路上继续叠加新能力。
- 不提交 `.env`、密钥、用户上传文件、会话数据库和本地输出。

## 二、逐步实施

### 第 01 步：固定代码基线与开发环境

**目的：** 确认从哪份代码开始，保证后续问题能够复现。

**操作：**

1. 查看 `git status`、当前分支与提交，记录在 `docs/implementation/01-baseline.md`。
2. 确认 Python 解释器与项目实际支持的版本，建立项目虚拟环境。
3. 核对 requirements 中的直接运行依赖，特别是 SQLite checkpoint 扩展；列出缺失项，不仅依赖其他包间接安装。
4. 新增 `requirements-dev.txt`，包含 pytest、pytest-asyncio、HTTP 测试依赖和现有代码检查工具，版本需经环境安装验证。
5. 检查 `tests/` 当前内容，建立测试配置。测试使用临时数据库和目录，不能读取真实密钥或触发付费服务。

**改动文件：** `requirements.txt`、`requirements-dev.txt`、`pyproject.toml`、`tests/conftest.py`、基线记录。

**检查方法：** 安装依赖后执行 `python -m pip check`，记录实际版本；运行已存在且可用的测试。无已有测试时如实说明，不用空测试通过代替项目验证。

**完成条件：** 环境可复现，依赖检查通过，确认已有测试范围和当前运行风险。

### 第 02 步：验证 Skill 与 Hook 接口，决定框架版本

**目的：** 在正式改造前确认框架能支持要接入的能力。

**操作：**

1. 使用当前锁定版本，检查 `create_deep_agent`、CompiledSubAgent、Skill 后端以及工具调用中间件实际接口。
2. 编写一个最小验证：使用可控模型和假工具，读取测试 Skill；工具执行前后经过包装；子 Agent 能返回结果。
3. 当前版本满足要求就不升级；不满足时，在隔离环境选择兼容版本组合，验证通过后更新锁定依赖。
4. 比较升级前后工具调用结构、流式节点输出、checkpoint 行为和默认工具列表。
5. 在 `docs/implementation/02-framework.md` 写明最终版本、接入接口与限制。

**改动文件：** 最小验证用例、依赖锁定文件、框架接入记录。

**检查方法：** `python -m pytest tests/test_framework_contract.py -q`。其中 Skill 测试应证明正文真实可读取，不能只证明配置参数被接受。

**完成条件：** 确定一个可运行的版本组合；确定主 Agent 和自行构建的子 Agent 分别怎样配置 Skill 与工具包装。

**禁止提前做的事：** 不照搬现行文档接口到旧版，不假设主 Agent 的 Hook、Skill 自动继承给所有子 Agent。

### 第 03 步：修复异步执行与生命周期管理

**目的：** 让基础调用链先具备稳定的异步执行能力。

**操作：**

1. 将 `agent/main_agent.py` 中同步 SqliteSaver 改为经过验证的异步 SQLite 保存组件。
2. 将连接建立和 Agent 初始化移入启动初始化函数，避免导入模块就打开数据库并构建模型。
3. 初始化加异步锁，重复调用复用同一已初始化对象。
4. FastAPI 启动时完成初始化，关闭时清理后台任务与数据库连接。
5. 保留后台任务引用；完成回调读取异常并清理引用。
6. 按最终框架版本选择流式模式，验证消息解析，不凭节点名称的旧假设认定最终结果。

**改动文件：** `agent/main_agent.py`、`api/server.py`、相关直接依赖。

**检查方法：** `python -m pytest tests/test_agent_lifecycle.py -q`；用可控 Agent 输出验证正常、报错与关闭三个路径。

**完成条件：** 异步流式执行和 checkpoint 保存能组合使用；导入无运行副作用；任务异常不被静默丢弃；关闭后资源释放。

### 第 04 步：为每轮任务建立独立记录

**目的：** 区分同一会话里的不同问题，防止结果写错轮次。

**操作：**

1. 保留 `thread_id` 标识会话，新增服务端生成的 `run_id` 标识一轮执行。
2. 新增运行上下文，携带 run_id、会话 ID、工作目录、截止时间与调用计数。
3. 在 `api/run_store.py` 用 SQLite 保存 runs；每条记录包含问题、状态、答案、错误、创建与结束时间。
4. `/api/task` 返回 thread_id 与 run_id；输出目录调整为 `output/session_<thread_id>/run_<run_id>/`。
5. 首版同会话已有任务运行时返回 409 和当前 run_id，不再启动第二轮；不同会话允许并发。
6. 状态更新基于 run_id，终态不能被晚到结果随意覆盖。

**改动文件：** `agent/runtime/context.py`、`api/run_store.py`、`api/server.py`、`api/context.py`、文件工具适配。

**检查方法：** `python -m pytest tests/test_runs.py tests/test_run_concurrency.py -q`。

**完成条件：** 同会话重复提交被拒绝；两会话互不串台；完成、失败和清理都定位到正确 run_id。

### 第 05 步：统一事件保存与进度推送

**目的：** 所有功能使用同一份执行记录，不再仅依靠控制台和临时 WebSocket 消息。

**操作：**

1. 定义事件字段：thread_id、run_id、event_seq、call_id、parent_call_id、执行对象、状态、时间。
2. 新增 `agent/runtime/events.py`，作为事件保存出口；SQLite 保存 events，序号在每轮内唯一且递增。
3. 先保存事件，再投递前端；断线不删除已保存事件。
4. `api/monitor.py` 保留旧方法作为适配，内部转到新出口。
5. 区分“模型提出调用”与“业务代码开始执行”，不要将两条开始记录误认为执行两次。
6. 保存最终答案和失败原因；参数记录做脱敏，避免泄露密钥和完整上传文档。

**改动文件：** `agent/runtime/events.py`、`api/run_store.py`、`api/monitor.py`、`agent/main_agent.py`。

**检查方法：** `python -m pytest tests/test_events.py tests/test_run_history.py -q`。

**完成条件：** 不连接 WebSocket 时仍可读取完整记录；记录与答案属于正确轮次；显示发送失败不会把查询结果改成成功或失败。

### 第 06 步：建立 Hook 的统一执行入口

**目的：** 让执行前检查和执行后处理真正进入调用链。

**首版 Hook：**

| Hook | 接入位置 | 处理内容 |
|---|---|---|
| before_run | 主任务开始前 | 绑定上下文，准备本轮限制 |
| before_delegate | 子 Agent 真实执行前 | 检查目标与调用条件 |
| before_tool | 工具业务函数执行前 | 参数、权限与次数校验 |
| after_tool | 工具返回或抛异常后 | 保存结果、错误与耗时 |
| after_subagent | 子 Agent 检查完成后 | 保存子任务结果与检查状态 |
| after_run | 整轮结束时 | 保存答案和最终状态 |
| on_error | 异常路径 | 分类错误、记录失败 |

这些是项目约定的 Hook 名称，不是直接复制的框架函数签名。

**操作：**

1. 新增 `agent/runtime/hooks.py`，先实现固定顺序执行，不建设任意插件排序。
2. 控制类 Hook 可拒绝动作；记录类 Hook 不改变已经发生的业务结果。
3. 用第 02 步确定的框架接口包装工具；对子 Agent 的自行构建执行器也明确接入。
4. 主 Agent 文件工具与框架默认工具同样纳入控制；无法纳入的工具禁用，避免绕过。
5. 清理无论成功、失败或取消都执行；记录失败需明确暴露，不能宣称已经持久化。

**改动文件：** `agent/runtime/hooks.py`、主 Agent 构建代码、工具包装适配。

**检查方法：** `python -m pytest tests/test_hook_pipeline.py -q`；通过假工具计数证明拒绝后实际函数调用数为零。

**完成条件：** 正常、拒绝、工具异常三条路径有明确执行顺序；没有重复执行；工具不能绕开 Hook。

### 第 07 步：在 Hook 中加入实际执行规则

**目的：** Hook 不只产生日志，还能限制真实动作。

**操作：**

1. SQL：使用只读账号，校验允许访问的表、单条只读语句、返回行数和数据库超时；不能只判断字符串以 SELECT 开头。
2. 文件：解析后的路径必须处于允许工作目录；检查上传文件名、下载接口及静态输出访问，避免工具校验之外的入口绕过。
3. 调用次数：主模型、子模型、自检、工具和重试分别记录，并受整轮总限制；调用前原子预留，不在返回后才计数。
4. 允许本轮的 Skill 目录只读；用户文件与任务说明目录分开。
5. 工具错误分类：临时网络失败允许有限重试；非法参数、无权限与缺配置不重试。
6. 将限制集中配置在 `config/runtime.yml`，以启动校验拒绝非法配置。

**改动文件：** `config/runtime.yml`、`agent/runtime/policies.py`、`tools/db_tools.py`、`utils/path_utils.py`、文件路由。

**检查方法：** `python -m pytest tests/test_tool_policies.py tests/test_call_budget.py -q`。

**完成条件：** 非只读 SQL、越界路径、次数耗尽均在执行前拒绝；重试、自检以及并发调用也被计入限制。

### 第 08 步：统一子 Agent 注册与触发入口

**目的：** 明确主模型选谁、框架如何调用、业务代码在哪检查。

**目标链路：**

```text
主模型提出 task 调用
 → 框架按注册目标路由
 → before_delegate 检查
 → 子 Agent 开始执行
 → 工具经过 before_tool / after_tool
 → 保存子任务结果
 → 返回主 Agent
```

**操作：**

1. 新增 `agent/subagent_registry.py`，使用稳定 ID：db、search、knowledge；显示中文名称与内部 ID 分开。
2. 注册表包含工具集合、模型配置、检查配置、允许的 Skill。
3. 新增 `agent/subagent_factory.py`，统一构建专家执行器并包装实际执行入口。
4. 子任务保存服务端生成的 call_id、run_id、目标、任务说明、状态和截止时间。
5. 无效目标在路由执行前拒绝；框架默认通用子 Agent 同样包装或明确禁用。
6. 保留框架 task 路由，不再另写一套循环调度器。
7. 将调用记录的主入口定为一个位置，防止中间件与执行器重复扣次数。

**改动文件：** `agent/subagent_registry.py`、`agent/subagent_factory.py`、`agent/runtime/delegation.py`、`agent/main_agent.py`。

**检查方法：** `python -m pytest tests/test_delegation.py -q`；用框架实际 task 路由验证，而非只测试注册字典。

**完成条件：** 三类助手可被调用，未知目标被拒绝；调用与返回可关联；前端显示助手名称；子任务真实执行经过 Hook。

### 第 09 步：新增子 Agent 结果检查与有限重试

**目的：** 处理“工具执行了，但内容没有满足任务”的情况。

**操作：**

1. 新增 `agent/reflection.py`，统一检查结果结构：判定、问题、缺失依据和修订指令。
2. 先做规则检查：空结果、标准化工具失败、缺少关键字段；再按任务开启异步模型检查。
3. 默认最多补充查询一次，修订任务写明具体缺少什么。
4. 依赖不可用直接返回明确状态，不靠模型编造结果。
5. 模型检查失败返回“检查未完成”，根据配置降级处理，不静默返回通过。
6. 用真实工具执行记录核对“是否查询了表结构”“是否完成网页检索”等要求。
7. 将检查事件接入统一出口，不再添加另一套 monitor 协议。

**改动文件：** `agent/reflection.py`、`agent/subagent_factory.py`、检查配置和事件类型。

**检查方法：** `python -m pytest tests/test_subagent_review.py -q`；覆盖空结果、缺来源、工具失败、检查模型失败、次数耗尽。

**完成条件：** 不合格结果最多再执行一次；服务失败与内容不足有不同处理；检查不是仅凭模型自述“已查询”。

### 第 10 步：保存合格结果并传给后续任务

**目的：** 后续搜索能够利用内部查询结果，并知道数据从哪里来。

**操作：**

1. 新增 `agent/results.py`，保存 result_id、run_id、来源、查询对象、时间范围、统计口径、原文引用和检查状态。
2. 原文较大时保存到本轮目录，SQLite 保存位置和摘要。
3. 只有经过检查的结果发布为可用摘要；不合格结果仍保存供追溯。
4. 执行搜索前，从服务端结果记录读取内部摘要，拼入任务说明。
5. 默认只使用本轮结果；跨轮使用需要明确记录来源轮次与时效，不能自动混用旧数据。
6. 内外结果不同就分别展示；首版不将关键词方向一致当成事实已被证明。

**改动文件：** `agent/results.py`、`api/run_store.py`、`agent/subagent_factory.py`。

**检查方法：** `python -m pytest tests/test_result_handoff.py -q`；比较搜索执行前收到的任务说明和保存的数据库结果。

**完成条件：** 合格结果可追溯并被后续任务读取；未通过检查的摘要不能满足前置条件；两轮、两会话不混用。

### 第 11 步：接入 Skill 的选择、正文与资源读取

**目的：** 将重复任务流程从常驻提示词中分离，并按需加载。

**操作：**

1. 创建 `skills/ecommerce-analysis/SKILL.md` 与指标参考，规定运营分析步骤。
2. 创建 `skills/report-writing/SKILL.md` 与报告模板，规定输出结构和引用方式。
3. YAML 保留角色、工具与简短常驻要求；迁出的详细流程不在两处重复维护。
4. 按第 02 步验证的后端映射只读 Skill 目录，避免默认虚拟文件系统读不到本地文件。
5. 请求新增可选 `skill_ids`；显式选择时校验并保证正文已加载，未指定时允许模型按元信息选择。
6. 记录 selected、loaded、resource_loaded 三种状态，分别代表选择、正文读取和附属资源读取。
7. 主 Agent 可见两个 Skill；子 Agent 按需显式配置，不假设自动继承。
8. 首版不执行 Skill 中任意脚本；模板不能覆盖输出目录与工具权限规则。

**改动文件：** `skills/`、`agent/runtime/skills.py`、`agent/main_agent.py`、`prompt/prompts.yml`、请求模型。

**检查方法：** `python -m pytest tests/test_skill_loading.py -q`；再完成一次真实框架文件读取验证。

**完成条件：** 指定 Skill 后可证明加载了正确正文；错误 ID 与越界资源拒绝；普通查询不被强制加载报告模板。

**注意：** 文档中写了某步骤，不等于运行时强制执行；下一步补代码约束。

### 第 12 步：实现运营分析流程的前置条件

**目的：** 指定内外对照流程时，确保搜索拿到真实内部结果。

**操作：**

1. 为请求增加明确业务模式：普通任务或内外对照；普通任务保留自由选择助手。
2. 显式选择 ecommerce-analysis 的内外对照流程时，服务端初始化步骤状态。
3. before_delegate 检查首次搜索是否关联有效数据库 result_id。
4. 数据库未完成时拒绝越序调用，并向主 Agent 返回下一步要求。
5. 数据库不可用时保存失败记录，可进入明确降级流程；最终答案不得假装已有内部指标。
6. 报告生成前核对所需查询状态和用户文件要求；不要求所有报告一律调用全部助手。
7. 将主模型重复越序请求计入总调用限制，避免持续拒绝却无限循环。

**改动文件：** `agent/runtime/workflows.py`、`agent/runtime/delegation.py`、`agent/results.py`、工具策略。

**检查方法：** `python -m pytest tests/test_workflow_order.py -q`。

**完成条件：** 越序搜索的业务函数未执行；内部查询完成后可继续；普通搜索不被误拦截；降级路径有明确状态。

### 第 13 步：增加总超时、取消和事件补发

**目的：** 长任务能结束，用户断线后仍能看到已有进度。

**操作：**

1. 总截止时间覆盖模型调用、检查和重试；每次外部请求还需自身超时。
2. 新增取消接口，例如 `POST /api/runs/{run_id}/cancel`，按运行记录定位后台任务。
3. 增加事件读取接口，例如 `GET /api/runs/{run_id}/events?after_seq=...`。
4. WebSocket 重连后按 event_seq 补发，前端按 ID 去重。
5. 超时和取消进入终态，不再安排新工具；线程或外部请求的晚到结果不能覆盖该终态。
6. 服务退出清理任务；首版不承诺重启自动恢复执行，将未完成记录标为中断并允许用户重试。

**改动文件：** `api/server.py`、`api/run_store.py`、`api/monitor.py`、运行上下文。

**检查方法：** `python -m pytest tests/test_run_cancellation.py tests/test_event_replay.py -q`。

**完成条件：** 超时与取消有明确状态，晚到结果无覆盖；断线重连可补读已保存事件。

### 第 14 步：前端联调与首版功能验收

**目的：** 把各模块组合成可实际使用的功能。

**操作：**

1. 前端保存 thread_id 和 run_id，显示 Skill 读取、助手开始、工具完成、检查、补充查询、失败与最终结果。
2. 技术 ID 放在展开详情中，用户主要看到动作和原因。
3. 显示忙碌、取消、超时与部分完成，不能统一显示“任务成功”。
4. 完成下方验收场景；保存真实执行日志，注明模型、环境和依赖版本。
5. 更新 README 与功能状态清单，区分已实现、已验证和后续功能。
6. 集成验证期间启动的服务在验收结束后停止，并记录端口与进程已释放。

**改动文件：** `api/static/index.html`、`README.md`、`docs/implementation/14-acceptance.md`。

**检查方法：** 运行全套相关测试，再进行真实模型和所需服务的最小联调；本计划的测试命令是未来执行步骤，不是已经通过的结果。

**完成条件：** 下方首版验收项都有匹配当前代码的记录，不以界面标签存在代替后端能力生效。

## 三、首版验收场景

| 场景 | 必须看到的结果 |
|---|---|
| 显式选择 Skill | 正确正文读取记录，任务使用对应说明 |
| 普通查询 | 不强制套用运营分析依赖顺序 |
| 子 Agent 调用 | task 请求、真实执行、工具记录、检查和返回能关联 |
| 内外对照查询 | 数据库结果可追溯，搜索任务实际收到内部摘要 |
| 越序调用 | 真实搜索函数调用数为零，返回明确原因 |
| 信息不完整 | 带缺失项重新查询，最多一次 |
| 依赖不可用 | 保留失败原因，不编造数据库指标或外部结果 |
| SQL、文件越界 | 在执行前拒绝，业务函数调用数为零 |
| 两会话并发 | 输出、摘要和消息分别归属正确会话 |
| 同会话重复提交 | 返回 409，不覆盖现有执行轮次 |
| 次数耗尽、超时、取消 | 不启动新动作，晚到结果不覆盖终态 |
| 刷新与重新连接 | 答案和已有事件可重新读取 |

无需在首版强制开展大规模准确率对照实验。先证明功能已经接通；后续若声称更准确、更快或更便宜，再测对应指标。

## 六、建议从哪里开始

第一轮只做 01–03：确认环境与框架接口，修复异步 checkpoint 和任务资源管理。第二轮做 04–08：让每次子 Agent 和工具调用都能记录、检查、拒绝。第三轮再做结果检查、摘要传递和 Skill。这样每轮交付都能运行和验证，也容易定位新增问题。
