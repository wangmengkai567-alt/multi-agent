## 1. 修复目标

停止继续叠加复杂业务协议，先稳定完成以下基本链路：

**用户请求 → 主助手分工 → 子助手调用工具 → 返回结果 → 主助手汇总 → 正文或 Markdown 交付。**

沿用当前 Python、Deep Agents、LangChain 和 LangGraph 技术栈，保留现有搜索、文档、数据库三个助手。本轮不替换执行内核、不升级框架、不新增嵌套委派；首版分工按顺序执行。

不以“已修改代码”“已接入 CI”或“模型返回了答案”作为完成依据。每一步必须有与最终实现匹配的执行证据；未通过的项目明确列为未完成。

## 2. 已确认的问题与基线

前几轮将计划、来源约束、对象身份、逐字需求登记、事实覆盖和最终交付耦合到同一条执行链，造成基本委派无法启动。

第 1 道真实业务题的失败记录显示：

1. 第一次计划自行填写 github.com 等搜索域，与当前“来源域必须由用户原文明确指定”的规则冲突。
2. 第二次计划使用 LangChain Deep Agents 等展示名称，原文是“LangChain 的 Deep Agents”，未满足连续原文匹配，进入发现对象校验并被拒绝。
3. 第三次计划将“委派子任务”改写为“子任务委派”，未满足逐字需求锚点要求。
4. 三次计划均未成功，未实际执行搜索、文档读取或专家分工；最终仍输出事实块，因缺少事实支持被拒绝。

交付协议还存在结构与业务约束不一致：事实池为空时 fact_ids 被限制为空，但 Schema 仍允许 kind=fact；后续业务校验又禁止空支持事实。没有合法计划和需求时，也缺少可用的正常限制说明分支。应在执行状态处明确失败，避免进入无法满足的终稿协议。

## 3. 保留与收敛范围

### 3.1 保留的基本功能与保护

- 主助手向搜索、文档、数据库助手委派明确任务，接收结果后汇总。
- 登录认证、资源归属、会话及工作目录隔离。
- 联网许可、数据库只读与表白名单、已绑定材料访问限制。
- 工具底层超时、受管理工作进程回收、取消、预算上限。
- 实际工具执行记录、真实来源及页表行等位置、明确失败原因。
- 正文和 Markdown 交付，以及实际文件内容、下载和所属关系检查。
- 已修复的 Windows 摘要历史文件名问题。

### 3.2 从基本执行链中移除的复杂前置条件

- plan_research 不再是搜索助手执行的必经入口。
- 模型不再为基本委派填写逐字对象名称、需求 anchor、发现事实 ID 或复杂需求图。
- 基本汇总不再要求模型为每个断言填写 fact_id、rid 和 coverage。
- 动态需求版本、发现对象、逐断言缺口及 dropped 生命周期，不再作为基本多智能体运行的必经步骤。

这是执行协议的收敛方案，不是关闭保护检查。取消逐断言覆盖协议后，仍必须保留真实工具记录和来源合法性检查；这些检查不能被描述为对全部自然语言事实的正确性保证。

实施时先确认依赖，再完整清理被替换实现、调用、提示词和状态接线。不保留新旧两套执行路径、不增加 fallback 或旧协议兼容分支，也不顺带重构无关功能。

### 5.1 主助手与程序的职责

- 模型：描述分工、解读实际返回结果、组织最终回答。
- 程序：签发身份、绑定权限与材料、安排执行、管理预算和超时、记录状态、提供真实来源、生成并交付文件。
- 权限、执行状态和工具结果真实性不由模型自行声明。

### 5.2 失败处理

参数错误返回准确原因；不可执行的任务明确失败。子任务失败时保留已经成功的结果和原始执行记录，但不得将整体任务标成全部完成。

不自动替换模型、引擎或工具，不重新执行结果不明确的有副作用操作，不扩大预算掩盖失败。没有有效结果时不生成虚构事实或成功文件。

## 6. 固定验收场景

验收使用真实应用入口和实际执行链，必要的外部依赖在隔离环境提供可控响应。只构造提示词或模型返回成功文本，不算工具与多智能体验收通过。

| 场景 | 必须取得的证据 |
| --- | --- |
| 1. 单个搜索助手 | 主助手实际委派；搜索工具执行；助手返回真实来源；主助手正确使用对应结果 |
| 2. 多个分工 | 各分工分别执行并返回；结果、状态、材料和来源不串任务；主助手能够汇总 |
| 3. 上传文档 | 实际读取绑定文件；保留位置和读取限制；不声称读取未支持内容 |
| 4. 数据库 | 允许的只读查询成功；越权查询被拒绝；返回结果属于对应分工 |
| 5. 失败与取消 | 工具失败、超时、取消后终态正确；执行资源释放；迟到结果不能改写终态或发布成功结果 |
| 6. Markdown 交付 | 最终正文成功写入并通过认证下载；UTF-8/CRLF 文件字节与应交付正文一致 |

补充回归必须覆盖认证、资源隔离、联网限制、数据库只读、来源合法性和预算；不能因简化执行协议而删除这些保护的有效断言。

先完成上述离线链路检查，再执行原第 1 道真实业务题。每道真实题结束后汇报并停止，不自动进入下一题或重跑。业务成功必须核对分工、工具、返回和交付证据，不能只看 run.status。

## 7. 变更控制与完成判据

### 7.1 控制新缺陷

- 先固定当前失败记录和验收场景，不在实施中不断增加功能或更换目标。
- 分步修改、分步验证；只有新增失败、实际改动或未覆盖要求才追加检查。
- 复用现有工具、资源回收和认证实现，避免无关技术栈变更。
- 旧用例逐项迁移到新契约，说明其验证义务如何保留；不通过吞异常、关闭校验、删除有效断言或恢复废弃功能取得通过。
- 历史数据保留；如果持久化结构必须改变，先在副本验证显式迁移，不自动改写生产数据库或兼容旧检查点续跑。
- 文本使用 UTF-8，保留已有 BOM，按项目要求使用 CRLF，并检查实际文件字节和空白。
- 只允许 git status；不暂存、提交、推送、切换分支或执行其他 Git 操作。

### 7.2 测试修改授权

本方案将相关测试夹具和断言迁移列为必要实施项。项目现有规则禁止未经明确请求新增或修改测试，因此实施前需要用户明确授权相关测试调整。本次编写文档不包含该授权，也不修改测试文件。

### 7.3 完成判据

只有满足以下条件，才能称为基本多智能体修复完成：

1. 六项固定验收场景均有匹配最终源码的执行证据。
2. 相应保护检查通过，被替换协议没有残留调用或兼容分支。
3. 相关回归通过；未通过或因夹具阻塞的项仍明确列出，不计为成功。
4. 第 1 道真实业务题完成并经证据核对；失败时如实报告并停止。
5. 最终说明实际改动、验证结果、保留限制与未完成项。

代码数量、修复轮数、工具调用次数以及测试通过总数，均不能替代上述验收。
