# 单对象检查范围、失败收尾与取消日志修复

本文保留该轮定位与验证过程。当前程序收尾、最终答复检查及跨问题验收见 [system-reliability.md](system-reliability.md)；下文无工具模型收尾方案已被程序生成的有限结果替代。

轮次 4bf31840-a3f2-4211-95ec-1cee0461bccf，问题为“请你帮我对比一下华为 Watch fit4pro 和 华为 Watch fit5，哪一个更推荐购买？”，2026-10-18 14:30:47 开始，14:35:48 超时结束。

## 已确认的问题

1. 最初是两个不同的并行任务，分别收集 FIT 4 Pro 和 FIT 5。上一轮引入原始 user_query 后，没有把它与 delegated_task 的检查边界明确分开。检查器因此要求 FIT 4 Pro 子任务补齐 FIT 5 和完整购买推荐；随后它的保留补查也被用于调查 FIT 5，造成分工串台。这是应用检查提示和任务上下文设计的问题。
2. 检查器还把多产品发布会视频中上下文不完整的价格片段归给当前产品。修订建议可能有错，不能把检查器的文字视为权威事实。
3. FIT 5 修订结果包含了与真实工具返回路径一致、但省略 http/https 协议的来源。原规则做完整字符串比较，因此仅格式差异便提前拦截，语义检查没有机会执行。
4. 两个任务结束允许的修订后，主助手把缺口改写成两个新任务。原去重只识别规范化后的相同描述，改写可以绕过它。第三个任务被接纳，第四个受子任务数量上限拦截；随后第三个仍可搜索，这并不表示那个被拒绝的请求执行了。前端旧文案把任务数量限制笼统描述成整轮额度用尽，容易误导。
5. 最后达到 300 秒总时限，框架取消异常携带内部 object 哨兵。直接 str(error) 把对象地址写入日志，前端又将取消显示成动作失败。

## 修改

- 为检查器单独传递实际委派说明 delegated_task，原始问题只作目的背景；禁止把其他并行分工、完整对比或推荐强加给单对象资料任务。执行器也收到同样的职责边界。产品对比提示要求区分必需决策维度和可选的首销日期、逐 SKU 价格等，不自动追查不存在的版本。
- 要求检查器确认多产品来源中数字的所属对象；片段不足时不能把另一个产品的价格判成当前产品的确定官方事实。串型号、编造参数、无依据断言仍不能通过。
- 仅对真实成功检索返回的完整 URL 修复遗漏的协议。路径、查询参数和来源必须吻合，不把域名扩成页面，不猜链接，不自动接受仍然缺少真实来源的内容。规范化后的正文同步用于后续检查和结果保存，原始工具证据保持不变。
- 普通模式下，当至少两个检索任务结束允许的处理且失败、并且没有仍在运行的检索任务时，进入收尾阶段。失败包含信息不足、检查未完成、模型/工具依赖失败及预算耗尽；仅一个任务失败不会关闭其他独立任务。执行层拒绝改写描述后的新搜索任务，主模型使用无工具的新上下文，仅接收通过检查的正文和明确标识的失败/未核实线索，汇总有限结论。内外对照工作流的前置条件不变。
- 取消事件保留 cancelled 状态并提供可读原因，达到总时限时显示“任务达到总时限，已取消当前操作”。前端也能将历史取消日志中的 object 地址替换为可读提示，无需改写原始记录。

总时限 300 秒、模型请求 60 秒、搜索请求 20 秒保持原配置。没有通过跳过检查或延长时限掩盖问题。
