# 18 · 现有故障的收敛修复方案

> 本文针对已发生的故障制定修复方案。2026-10-24 已按用户“继续修复”指令落实下述核心代码改动；本轮只做静态检查，未追加运行测试、真实模型或检索实跑，不宣称端到端验收通过。此前失败记录继续保留在17-repair-implementation.md。

## 结论

当前剩余故障集中在：同一对象缺少稳定身份；需求被重复/扩张登记；模型承担了不应由它负责的ID记账和硬约束覆盖判断；终稿分析可夹带新事实。继续增加实跑次数不能代替修正这几处设计。

## P0：先修正对象与需求契约

### 1. 对象身份与展示名称分离

现有 source_policy.source_satisfies 对 model 做字符串全等：需求是“华为 FIT 5”，事实可能写“华为 WATCH FIT 5”“华为 WATCH FIT 5系列”或“华为 WATCH FIT 5 Pro”。最后一轮这三种事实被一起判为覆盖，程序按字面约束拒绝整份终审。

修复：

- 保留原始名称和原始anchor；以程序签发的object_id作为关联身份。
- 规范名/别名必须有本轮来源或明确审核依据，确认后才关联同一object_id；不能靠删空格、删除Pro/系列后缀强行合并。
- 标准版、Pro、地区版分别保留variant；系列级事实只有来源明确适用于指定产品时才能支持它。
- 身份尚未确认的事实不用于覆盖该对象，继续保留其真实scope及未确认原因。

落点：requirements.py、facts.py、source_policy.py、reporting.py、review_contract.py。结果：同一实体的不同名称不再因字面不同误拒，Pro也不能冒充标准版。

### 2. 必需需求、研究工作和原文来源分开

最后一轮原题只有“三款价格、横向比较、购买建议”，却登记出13个需求：包含每款发布状态、每款固定两三个参数、重复原始整句等。逐字anchor存在，并不能证明这些都是用户必需条件。

修复：

- 必需需求登记为可分别判定的叶子项：三款各自的双11价格、综合比较、购买建议；参数/型号核实是服务这些需求的研究工作，用户未单独要求时不新增完成门槛。
- 用“原文子句→一个或多个rid”关系保存来源；已由叶子项承接的整句不再额外变成重复必需项。
- 无法证明已承接的子句进入显式待判定项，保持unknown，不能因anchor部分相同就删除。
- 来源渠道、地区、版本等记录为事实实际适用条件；不因规划说明写了这些词，就变成用户新要求。

落点：requirements.py、task_plan.py、delegation.py。结果：缺价格就准确标价格缺口，不再被新增或重复条件拖住。

## P0：把硬约束从审核模型手中收回

### 3. 先限定合法支持集合，再做语义审核

现有终审模型反复用型号/范围不匹配的事实标covered，甚至给“covered + 空支持集”。程序拒绝是必要防护，但让模型反复猜相同约束无法稳定完成任务。

修复：

- 审核前由程序按object_id、variant、有效事实版本、来源条件和实际终稿采用集合计算每个rid的合法候选支持ID。
- Schema按每个rid限制其允许支持ID；没有合法候选时不提供covered选项。这是生成前的契约约束，不是事后把错误结果自动降级为通过。
- 模型只判断合法候选是否在语义上充分满足该需求，并逐条审核断言；程序负责ID完整性、硬范围匹配及最终聚合。
- 比较/推荐通过其已审核分析及依赖关联需求；不能仅凭若干参数事实就声称已完成价格比较或购买建议。
- 覆盖资料是否齐全与正文是否真实分别记录。合法的有限答复允许partial；结构或语义审核未完成仍明确失败，保留已审核子任务事实，不伪造兜底答复。

落点：review_contract.py、reflection.py、answer_review.py。结果：缺资料可以形成诚实有限答复；非法支持不能被发布。

## P1：简化终稿生成

### 4. 程序计算采用/未采用集合

最后一轮首稿将同一事实同时列为已用和omitted；这类集合记账错误耗掉了终稿修订机会。

建议调整DeliveryDraft：模型输出文本块和真实支持ID，程序从文本块计算used与unused，不再要求模型重新抄写完整unused集合。可证明的重复/过时等原因由已有事实解析结果记录；其他明确记为“未被终稿采用”，不能默认“不重要”。是否因未采用而漏答，仍由需求覆盖单独约束，不能因此标complete。

若保留细分省略原因，补充阶段只允许给程序已算出的unused ID填写原因，不允许模型改变集合。删除旧的双重记账协议，不增加兼容分支。

落点：delivery.py、finalization.py、answer_review.py。

### 5. 分析不能成为新增事实的入口

实际终审曾把“Apple Watch仅适配iPhone”认作常识性合理推导并放行，但本轮支持ID没有这项事实；“专业度最高”“预算有限更合适”也不能从不完整参数或缺失价格推出。

修复：

- 将可独立核查的外部断言拆为事实块；分析只能使用已审核的事实关系，不能把常识补写当作推导。
- 比较明确指标、对象、适用条件；缺少同口径数据时不生成全体排名。
- 推荐写清依据和条件；价格未知时不能给性价比排名，资料不足时明确尚不能判断。
- 优先对比较/计算采用结构化指标和依赖；自然语言推导仍需独立语义审核，不承诺仅靠ID即可消除模型误判。
- 保留程序生成limitation的现有单一路径。

落点：delivery.py、finalization.py、reflection.py、review_contract.py。

### 6. 修订只修当前问题，减少无效生成

- 保留本次已补的准确错误ID、原稿审计及修订原稿输入；原稿明确是不可信待修内容，fact_pool仍是唯一事实来源。
- 首次报告、修订保底、终稿各自使用已实现的预算边界；R3仅重审，不重复搜集或生成报告。
- 审核输入只含当前合法事实、精确claim和需求，不重灌已结束的研究对话。
- 保留真实超时上限，不以无限重试或扩大预算掩盖流程问题。

## 2026-10-24 实施记录

本节记录代码变更，不将历史验证结果当作新协议的验收结果。

### 已接入的修复

1. **对象身份**：plan_research 要求逐字 object_name，由程序签发 object_id；报告保留来源名称和 identity_evidence，审核逐事实返回 object_match 及原因。没有有效身份引文时 Schema 不提供对象绑定选项；不同版本或未确认身份使用 null。来源名称不再与需求 model 字符串全等比较；其他显式范围维度仍受硬约束。
2. **需求与研究支持分离**：RequirementSpec 明确 kind，任务事实、主助手比较/推荐分别登记；investigations 是研究工作。无专属事实项的任务获得 required=false 支持项，不进入终稿必需清单，不触发“缺少必需需求”的补查。重复对象及同对象、同条件的重复需求被拒绝；规划异常整批回滚。
3. **原文承接关系**：requirement_links 记录原始子句对应的 rid/object_id；已承接整句不再重复登记。移除已登记片段与常见连接词后仍有未承接文字时，登记 kind=unresolved，只允许 unknown。该处理保守保留待判定内容，不能代替自然语言语义完整性审核。
4. **审核候选集合**：coverage 改为以 rid 为键的对象，每项 status/fact_ids/claim_ids。程序逐 rid 计算合法候选 ID 和状态，在 Schema 中限定；没有支持时不提供 covered，covered 分支要求非空支持。模型判定后，按真正通过、未过时、未冲突及终稿实际采用的事实重新验证，非法覆盖明确拒绝，不自动改成通过。
5. **比较与推荐**：终稿分析块必填 analysis_kind=comparison/recommendation/deduction。综合需求只接受相应类型且通过终审的 claim_ids，事实依赖由程序展开；覆盖全体对象的综合不能漏掉请求对象。事实需求只接受合法 fact_ids。
6. **终稿采用集合**：DeliveryDraft 顶层仅含 blocks，已删除要求模型填写 omitted 的旧协议。程序计算 used_fact_ids 和未采用项，未采用原因记 not_selected，不推定其不重要。是否漏答仍由实际终稿的需求覆盖判定。
7. **限制分析越界**：生成与终审均明确要求外部断言使用已核实事实，不接受常识补写、缺依据的全体排名或缺价格的性价比推荐。推导仍经过独立语义审核，程序 ID 合法不等于推导正确；limitation 继续由程序生成。
8. **衔接与审计**：终审更新必需覆盖时保留研究支持记录；未知覆盖行统一包含 claim_ids。审核后来源保留身份、值和日期证据及冲突/过时事实的来源记录。既有原稿审计、针对错误的单次修订、预算预留、R3仅重审和恢复 owner 机制保留。
